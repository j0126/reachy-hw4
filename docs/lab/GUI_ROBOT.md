# Motion Lab 실제 로봇 사용법

로봇 상자는 **창 위쪽(탭 위)**에 처음부터 떠 있다(2026-11-13). 연결 전에는 오른쪽 위 `로봇 상자` 버튼으로 숨기거나 다시 열 수 있고,
연결된 동안과 **② 실험** 탭 백엔드가 `실제 로봇 (measured)`일 때는 숨길 수 없다. 그래서 ① 모션 탭에서도 연결·Wake-up·토크 OFF를 바로 누를 수 있다.
버튼을 누른 동작만 실행된다. 별도 승인 창은 없다. AI 에이전트는 이 버튼을 누르지 않는다 (CLAUDE.md 규칙 3).

## 버튼

| 버튼 | 하는 일 |
|---|---|
| 연결 | 로봇 상태를 읽고(GET) SDK 클라이언트 1개로 연결한다. 토크가 꺼진 로봇이면 지금 자세에서 토크를 켠다 (`enable_motors`, 움직이지 않음) |
| Wake-up | SDK 1.11.0 Wake-up: INIT까지 2초, roll 20° 갔다 오기. 정지 뒤 INIT로 돌아갈 때도 쓴다 |
| ▶ 실행 (실제 로봇) (② 실험 탭 위쪽) | 표에서 고른 시행 1개: INIT → 시행 → INIT. 표의 정책 검사를 통과한 시행만 실행된다. 버튼에 실행할 곳이 나온다 (MuJoCo면 `▶ 실행 (MuJoCo)`) |
| ▶ 실제 로봇 재생 (① 모션 탭) | 보이는 모션·변형을 1번: R2 시행 1개와 같다(같은 검사·기록, 결과 탭에 들어감). INIT 대기일 때만 켜진다. 옆 글자가 로봇 상태이고, 연결 전이면 '위쪽 로봇 상자에서 연결' 링크(누르면 상자가 열린다, 탭은 그대로) |
| ■ 정지 | 0.3초 동안 감속한 뒤 그 자리에서 멈춘다 (토크는 켜진 채). 첫 명령 전에 누르면 '실행 취소' |
| 토크 OFF | "머리를 받쳤나요?" 확인 뒤 토크를 끄고 연결을 닫는다 |
| 연결 끊기 | 연결만 닫는다. 토크는 끄지 않는다 (창 닫기도 같음) |
| 새로고침 | 상태만 다시 읽는다 (명령 없음) |

상태 줄: `INIT 대기 · 시행 가능 · 토크 ON · 연결 열림`. 토크는 실제로 다시 읽은 값만 ON/OFF로 표시하고, 그 밖에는 UNKNOWN이다.
마우스를 올리면 근거가 보인다.

## 첫 R1 pitch +2° 순서

1. `.venv\Scripts\python -m reachy_motion gui` → ② 실험 → `실제 로봇` (창 위쪽에 로봇 상자가 나온다).
2. IP `192.168.0.15` · 포트 `8000` → **연결**.
3. 상태가 `연결됨 · Wake-up 필요`이면 **Wake-up**. 대시보드로 이미 깨운 로봇이면 바로 `INIT 대기`가 된다.
4. 동작 확인 (R1) → 축 `pitch` · 진폭 `10`(기본값) · 방향 `+` → 표 1행 → **▶ 실행** (약 6초).
   진폭 기본값은 가장 큰 단계(머리 10°, z 5 mm, 안테나 30°)이고, 축을 바꿔도 고른 단계가 유지된다. 2°는 실제 로봇에서 거의 움직이지
   않는다(아래 '작은 명령'). 시행이 끝나면 상자에 `시행 끝 · 진폭비`가 나오고, 0.5 미만이면 "진폭을 키워 보세요"라고 알린다.
   진폭은 직접 입력해도 된다(Enter; 회전 0.1–15°, z 0.1–8 mm, 안테나 0.1–45°, 같은 정책 검사). 여러 진폭의 결과는 결과 탭 `R1 진폭비` 그림.
5. 표 상태 `완료` → **결과 보기 →** (RMSE · Peak · Lag · 진폭비, data_kind measured).
6. 끝: **연결 끊기** (깨어 있는 채 대기), 또는 머리를 받치고 **토크 OFF**.

R3는 시행이 끝나면 바로 판정이 나온다: 무너졌으면 상자에 빨간 `R3 사다리 끝 — D … s에서 추종이 무너짐`, 더 짧은 단계는 `거부`.
진폭 사다리(D 고정)는 실제 로봇에서 D ≥ 1 s, A 10°부터 한 단계씩: 무너지면 `R3 진폭 사다리 끝 — A …°에서 추종이 무너짐`, 더 큰 A는 `거부`.
R2는 확정 모션 E/N을 하나씩 실행한다. 발표 데모는 ① 모션 탭에서 모션·변형을 고르고 **▶ 실제 로봇 재생**(연결·Wake-up은 창 위쪽 로봇 상자에서 한 번, 탭을 옮기지 않는다). R3는 Duration 사다리를 한 단계씩 진행하며, 짧은 D는 앞 단계를 실제 로봇에서 잰 뒤에만 실행된다.
로봇에서는 '모두 실행'이 없다.

## 이상할 때

- **■ 정지**를 누르고, 머리를 받치고 **토크 OFF**를 누른다. 안 되면 전원 스위치를 끈다.
- 같은 로봇을 대시보드·CLI·다른 PC에서 동시에 제어하지 않는다. SDK에는 제어 잠금이 없다.
- 연결이 실패하면 상자에 원인이 한 줄로 나온다. 토크를 켠 뒤에 실패했으면 토크가 UNKNOWN으로 표시된다. 이때는 머리를 받치고 대시보드나 전원 스위치로 끈다.
- 연결 확인 기준 (2026-11-12 실측 반영): 명령을 보내기 전 1초 동안 머리가 0.5°보다 많이 움직이면 다른 무언가가 움직이는 것이므로 멈춘다. 토크를 켠 뒤에는 2°까지 허용한다(실제 로봇에서 0.53°가 두 번 나와 연결이 실패했었다). 토크 OFF 뒤에는 상태 메시지를 최대 3개 읽어 `disabled`를 확인한다(첫 메시지는 명령 전 것일 수 있다).

## 효과음 (Expressive 4개, 2026-11-14)

확정 모션 파일의 효과음 큐를 **로봇 내장 스피커**로 낸다(사용자 결정 "로봇 스피커로"). 설정은 ① 모션 탭 `효과음` 줄이다.

| 모션 | 소리 (모션 시작부터) | 파일 |
|---|---|---|
| aha_recommend E | 0.85 s, 번뜩 고개를 드는 순간 | `motions/sounds/aha.wav` (올라가는 종소리 두 번, 0.5 s) |
| success E | 0.3 s, 튀어 오르는 순간 | `motions/sounds/success.wav` (올라가는 아르페지오, 0.6 s) |
| failure E | 0.2 s, 고개를 떨구기 시작할 때 | `motions/sounds/failure.wav` (내려가는 단조 두 음, 0.75 s, 조금 작게) |
| boredom E | 4.9 s, 처지기 시작할 때 | `motions/sounds/boredom.wav` (한숨 같은 낮은 소리, 1.1 s, 아주 작게) |

- Neutral 4개는 소리가 없다. 음원은 직접 합성한 원본 소리다(`reachy_motion/sound.py`). 같은 이름으로 덮어쓰면 바뀐다.
- 소리 규칙(V/A 설계 목표에서): valence → 음의 방향·조(긍정 = 올라감·장조, 부정 = 내려감·단조), arousal → 빠르기·높이·크기(aha·success 빠르고 높게 -6 dBFS, failure 느리게 한 옥타브 아래 -8 dBFS, boredom 아주 느리고 낮게 -10 dBFS). 밝기(2 kHz 위 에너지, computed): aha −9 dB, success −2 dB, failure −54 dB, boredom −45 dB.
- 출력: `로봇 스피커`(GUI 기본) / `노트북 스피커`(대체, MuJoCo 재생도) / `끄기`. `♪ 소리 듣기`는 노트북으로 한 번 들어 본다(로봇에 보내지 않음).
- 동작: `▶ 실제 로봇 재생`(또는 실험 탭 R2 `▶ 실행`)을 누르면, 모션을 시작하기 전에 로봇의 미디어 상태를 읽고(`GET /api/media/status`)
  음원을 로봇에 올린 뒤(`POST /api/media/sounds/upload`, 연결마다 파일당 한 번), 모션 스트림이 큐 시각에 닿는 tick에
  `POST /api/media/play_sound`를 보낸다(별도 스레드, 50 Hz 실행기를 막지 않음). 근거: SDK 1.11.0 `daemon/app/routers/media.py:41-103, 207-262`.
- 소리 준비가 실패하면(로봇 daemon에 미디어 없음, 업로드 실패) 상자에 빨간 글자로 나오고 **모션만** 실행된다.
- 소리가 머리를 움직이지 않는다: daemon은 '흔들림(wobbling)'이 켜져 있으면 소리에 맞춰 머리를 흔드는데, 연결 순서가 흔들림을 끈다
  (`backends/robot_connect.py:311, 409`). 다른 앱이 흔들림을 다시 켜지 않도록 같은 로봇을 다른 앱과 동시에 쓰지 않는다.
- **실제 로봇에서는 아직 시험하지 않았다.** 우리 연결은 로봇의 카메라·오디오 파이프라인을 해제한다(`media_backend="no_media"`). 소스로는
  daemon의 소리 재생이 그와 별개라 나와야 하지만, 처음 한 번 로봇 앞에서 소리가 나는지 확인한다. 안 나면 `노트북 스피커`로 바꾼다.
- 시각 보정: 머리는 명령보다 약 0.19 s 늦게 움직이고(실측), 스피커 쪽 지연은 아직 재지 않았다. 소리가 먼저 들리면 `시각 보정`을 +로.
- 기록: 시행의 `manifest.json` `connection.sound`(출력, 파일, sha256, 로봇 경로, 큐 tick, 요청 시각·걸린 ms), 연결 기록 `sound_*.json`.

## 알려진 제한

**작은 명령은 거의 움직이지 않는다** (2026-11-12 실측, measured; 관절 변화는 SDK IK 계산값, computed).

| 명령 | IK가 요구한 Stewart 관절 변화 (computed) | 실측 (measured) |
|---|---|---|
| R1 yaw +2° (2번) | 6개 모두 0.6° | 관절 0° (안 움직임), 진폭비 0.18 · 0.12 |
| R1 pitch +2° | 최대 1.4° | 관절 ≤ 0.5°, 머리 +0.4°, 복귀 안 함, 진폭비 0.20 |
| R1 yaw +10° | 최대 3.2° | 진폭비 0.69, 복귀 뒤 4.2° 남음 |
| R1 오른쪽 안테나 +5° | 안테나 모터 5° (IK 없음) | 진폭비 0.77 |
| R3 pitch 20° D 1.0 s | 최대 14.5° | 진폭비 0.92 |
| R2 aha_recommend E | — | 진폭비 0.99 (yaw) |

명령한 관절 변화가 약 1° 이하이면 모터가 거의 움직이지 않는다. 시행마다 1회씩이라 반복 측정이 필요하다.
2026-11-13에 다시 잰 값(measured): yaw +10° 진폭비 0.61, z +5 mm 0.62 (같은 경향).

**목표와 실제가 다른 이유** (2026-11-12 22:36–22:53 실측, measured; 관절 목표는 명령 자세의 SDK IK, computed)

| 시행 | 진폭비 | Lag (r²) | RMSE (지연 포함) → 지연 보정 RMSE |
|---|---|---|---|
| R1 yaw +10° | 0.53 | 355 ms (0.31, 참고만) | 4.13° → 3.50° |
| R1 z +5 mm | 0.72 | 263 ms (0.71, 참고만) | 1.53 mm → 1.13 mm |
| R3 pitch 20°, D 1 s | 1.03 | 188 ms (0.97) | 3.84° → 1.39° |
| R2 aha_recommend E (yaw) | 0.97 | 193 ms (0.95) | 5.40° → 2.27° |
| R1 오른쪽 안테나 +30° | 1.01 | 68 ms (1.00) | 2.10° → 0.57° |

- 안테나(모터 하나가 바로 움직임)는 진폭 100%, 지연 68 ms다. PC → SDK → daemon 명령 경로는 정상이다.
- 머리(Stewart 모터 6개)는 각 모터가 목표 관절각에서 2–7° 떨어진 곳에서 멈춘다(실측 관절 − IK 목표, 정지 구간 평균). yaw +10°에서는
  stewart_2가 목표 변화 2.6° 중 0°만 움직였고, 다른 관절도 목표 변화의 40–80%만 움직였다. 6개가 머리로 묶인 닫힌 링크라 한 모터가 덜 가면
  머리 전체가 덜 간다. 돌아올 때도 다 오지 못한다(yaw +10° 뒤 +2.5°, R3 pitch 20° 뒤 +4.4°에서 멈춤).
- 큰 동작(20°, aha)은 진폭을 거의 다 채우고, 오차의 대부분은 약 0.19초 지연이다(지연을 빼면 RMSE가 1/2–1/3).
- SDK 설정(고정): Stewart 모터는 위치 제어(operating_mode 3)에 **P=300, I=0, D=0**, 안테나·몸통은 P=200, I=0, D=0
  (`reachy_mini/assets/config/hardware_config.yaml:57-164`, daemon이 연결 때 적용 `daemon/backend/robot/backend.py:81-91`).
  P만 있으면 모터는 오차에 비례한 힘만 내고, 남은 오차를 없애는 I 항이 없다. 그래서 머리 무게와 기어 마찰을 이길 만큼 오차가 커지기 전에는
  움직이지 않고(데드밴드, 지연), 그만큼의 오차를 남긴 채 멈춘다(정상 상태 오차). 이 해석은 제어 원리에 따른 설명이며, 게인을 바꿔 확인하지는
  않았다(SDK·daemon 고정, CLAUDE.md 규칙 2·3).

연결 끊기는 연결할 때 해제한 daemon 미디어(카메라·소리)를 되돌리지 않는다. 모션 실험과는 무관하다.

## 오프라인 검증

`.venv\Scripts\python -m unittest tests.test_gui_robot -v`

실제 GUI 경로를 클릭 순서대로 확인한다: 연결 → Wake-up → R1 pitch +2° → 토크 OFF.
GUI 기본 연결(`SdkBackend`)을 그대로 쓰고, SDK 클라이언트만 SDK daemon 코드 하네스로 바꾼다. 네트워크는 쓰지 않는다.
