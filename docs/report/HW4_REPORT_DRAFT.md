## 1. SDK가 로봇을 움직이는 방법

### 1.1 `goto_target()`의 경로 [S]

- **보간 위치**: 클라이언트는 보간하지 않는다. WebSocket `TaskRequest`를 받은 daemon이 `GotoMove`를 만든다.
- **시작점**: **현재 측정 자세**(`get_present_head_pose`)에서 시작해, 목표까지 `duration` 동안 보간한다.
- **평가 주기**: `play_move`가 100 Hz로 평가해 목표를 갱신한다. 50 Hz 제어 루프가 최신 목표를 IK에 넣고 모터에 보낸다.
- **호출 대기**: 호출자는 `duration + 1 s`까지 기다린다.
- **주의할 기본값**
  - `body_yaw` 기본값은 0.0이다. 생략하면 몸통이 0°로 돌아간다. 유지하려면 `None`을 준다.
  - 루프는 `t < D` 동안만 평가하고 끝 목표를 다시 쓰지 않는다. 그래서 LINEAR는 끝점이 g/D만큼 덜 간다(D = 0.3 s, g = 10 ms면 3.3 %).
- **그림**: `results/phase1/figures/fig5_command_pipeline.png` (명령 경로)

### 1.2 보간법 4종 [S][C]

정규화 시간 τ = t/D, 위치 s(τ), 피크 속도 = k·A/D.

| 방법 | s(τ) 특징 | 피크 속도 계수 k | 비고 |
|---|---|---|---|
| linear | 등속 | 1 | 시작·끝에서 속도 계단 (가속 무한대) |
| minjerk | 10τ³ − 15τ⁴ + 6τ⁵ | 1.875 | 가속도까지 연속인 유일한 방법 |
| ease_in_out | 양 끝 완만 | 2 | |
| cartoon | 예비 동작·오버슈트 | **5.595** | 시작 전 −10.0 %, 목표 뒤 +10.0 %로 **명령 자체가 구간 밖으로 나감** |

- 그림 1: `results/phase1/figures/fig1_interpolation_normalized.png` (정규화 위치·속도)
- 그림 2: `results/phase1/figures/fig2_interpolation_physical.png` (물리 단위)
- 그림 4: `results/phase1/figures/fig4_endpoint_shortfall.png` (끝점 미달)
- 표: `results/phase1/interpolation_characteristics.csv`, `interpolation_peaks_physical.csv`

### 1.3 머리 자세 → 모터 각도 (IK) [S][C]

- **입력**: 머리 자세(roll·pitch·yaw + x·y·z, 4×4 행렬)와 몸통 yaw
- **출력**: 몸통 yaw 1개와 Stewart 관절 6개
- **엔진**: 기본값 `AnalyticalKinematics`(Rust, 닫힌 형식)
- **자동 body yaw 모드**: yaw를 조용히 제한한다. 머리–몸통 상대 yaw 65°, 몸통 160°(`analytical_kinematics.py:88-89`).
- **IK 실패**: 해가 없으면 NaN이 나온다. daemon은 경고만 남기고 **직전 관절 목표를 유지**한다(조용히 멈춤). 클라이언트는 성공으로 받는다.
- **표·그림**: `results/phase1/ik_pose_table.csv`, `ik_sensitivity_neutral.csv`. 그림 3 `fig3_goto_joint_space.png` (goto의 관절 공간 궤적)

### 1.4 목표를 보내는 주기 [S][C]

- **제어 루프**: 실제 로봇·MuJoCo·mockup 모두 50 Hz다.
- **tick 순서**: 실제 로봇은 tick마다 "이전 IK 결과 쓰기 → 읽기 → IK"다.
  - 머리 명령은 한 tick(20 ms) 늦게 모터에 간다.
  - 안테나는 IK가 필요 없어 머리보다 약 20 ms 앞선다.
- **명령 경로 지연 모델**: 실제 로봇 30–40 ms.
- **명령값 기록**: 명령값(target)은 공개 채널로 나오지 않는다. 그래서 HW4 실행기가 명령을 직접 기록한다. 측정은 도착 시각과 함께 기록한다.

### 1.5 관절 한계 밖 목표 [S][D]

- **Stewart 한계** (URDF = MJCF = EEPROM): s1·s3 [−48, +80]°, s2 [−80, +70]°, s4·s6 [−80, +48]°, s5 [−70, +80]°
- **SDK는 Stewart 관절 한계·속도·가속·충돌을 검사하지 않는다.**
  - 펌웨어 위치 한계(EEPROM)가 설정돼 있으면 그 모터 하나만 자른다.
  - 그 결과 다른 다리와 자세가 맞지 않게 된다.
- **공식 문서와의 차이**: 공식 문서의 roll·pitch ±40°는 1.11.0이 클램프하지 않는다(업스트림 이슈 #1449).
- **자동 body yaw의 wrap**: 머리 yaw가 ±180°를 넘나들면 몸통 목표가 한 표본 사이에 약 229–275° 뒤집힌다. NaN이 아니므로 그대로 전송된다.

## 2. 표현 모션 설계

### 2.1 시나리오 (Term Project: Reachy Café)

| 범주 | 모션 | 상황 |
|---|---|---|
| (A) 의도 | `aha_recommend` | 추천 메뉴를 정하고 손님에게 보여 주기 직전 |
| (B) 상태·감정 | `boredom` | 손님이 없어 지루함 |
| (C) 반응 | `success` / `failure` | 주문 처리 성공·실패에 대한 반응 |

- 트리거: 버튼 하나(키 입력·스크립트와 같은 역할). Motion Lab ① 모션 탭 `▶ 실제 로봇 재생`(실제 로봇) · `▶ MuJoCo 재생`(시뮬레이션), CLI `play`·`sim-play`
- Term Project에서는 `MotionService.play(name, variant)`로 연결한다.

- 효과음: Expressive 4개는 로봇 내장 스피커로 소리를 낸다. 직접 합성한 소리다. aha(0.85 s, 올라가는 종소리 두 번), success(0.3 s,
  올라가는 아르페지오), failure(0.2 s, 내려가는 단조 두 음 "어-어"), boredom(4.9 s, 한숨 같은 낮은 소리).
  소리 규칙(V/A 설계 목표에서): valence → 음의 방향·조(긍정 = 올라감·장조, 부정 = 내려감·단조), arousal → 빠르기·높이·크기(aha·success 빠르고 높게 -6 dBFS, failure 느리게 한 옥타브 아래 -8 dBFS, boredom 아주 느리고 낮게 -10 dBFS). 밝기(2 kHz 위 에너지, computed): aha −9 dB, success −2 dB, failure −54 dB, boredom −45 dB.
  근거: 슬픔은 소리로 가장 잘 전달됐다(Löffler 외, HRI 2018). 강의 자료 [09]의 Reachy Mini 자극도 소리를 포함했다.
  Neutral은 과제대로 소리가 없어, 네 모션 모두 E와 N이 움직임·안테나·소리에서 다르다. 추종 측정(R2·R3)은 모터만 보므로 소리와 무관하다.
  소리가 잘 읽히는지는 사람 평가를 하지 않았다(설계 근거만). 실제 로봇 내장 스피커에서 네 소리 모두 재생되는 것을 사람이 들어서
  확인했다(2026-11-14; 재생 요청 71–90 ms [pc_measured], `results/lab/20261114_002724_robot_R2`, `20261114_004526_robot_R2`).

### 3.4 실제 로봇 한계 시험 [M] — **빈 절 (측정 뒤 작성)**

- **절차**
  - 시뮬레이션을 먼저 하고, 작고 느리게 시작해 한 번에 한 설정만 바꾼다. 첫 이상에서 멈춘다.
  - 순서 (Motion Lab ② 실험 탭, `docs/TEAM_GUIDE.md` §4): 연결 → Wake-up → R1 축별 10° 동작 확인 → R3 pitch 20° minjerk, D = 1.0 → 0.6 → 0.4 → 0.3 → 0.25 → 0.2 s
  - 한 단계씩 결과를 보고 `▶ 실행`한다. 앞 단계가 아래 판정 기준을 넘으면 GUI가 다음 단계를 거부한다(같은 연결 안, `robot_r1.r3_step_problems`). 그 단계가 무너진 지점이다.
  - D < 0.2 s는 실제 로봇에서 하지 않는다(0.15 s는 관절 가속이 aha E보다 크다, 3.2).
  - 진폭 사다리(선택)는 D 사다리를 마친 뒤 D 1.0 s에서 A 10 → 20 → 30°로 한 단계씩 한다. 실제 로봇은 D ≥ 1 s만이다(A 30°를 D 0.2 s에 하면 관절 가속 3521 °/s²로 aha E의 2941 °/s²를 넘는다 [C]).
- **기록**
  - 명령: 보낸 값과 전송 시각
  - 측정: `get_current_head_pose`, `get_current_joint_positions`와 도착 시각
  - 위치: 실행 폴더 `commands.csv`, `present_measured.csv`, `ticks.csv`, `manifest.json`
- **무너짐 판정** (다음 단계 거부 기준, `robot_r1.R3_LIMITS`): 진폭비 < 0.8, 지연 보정 RMSE가 진폭의 15% 초과, 오버슈트가 진폭의 15% 초과, 지연(r² ≥ 0.9)이 같은 사다리 D 1.0보다 100 ms 넘게 늘어남, 완료 못 함·S2·S3 정지·오류. 사람이 본 떨림·소리·열도 포함한다.
  - 과제의 무너짐 종류와 수치: lag = 지연, overshoot = 오버슈트, clipping = 진폭비 감소, shaking = **정지 중 떨림 RMS**(정지 구간에서 직선 추세를 뺀 측정값의 RMS, 표시만 함), motor error = 완료 못 함·S2·S3·오류(모터 오류 레지스터는 허용된 GET으로 읽을 수 없어 사람이 LED·소리·열로 확인).
  - 기준은 실측 기준선(D 1.0: 지연 184–188 ms, 지연 보정 RMSE 1.39–1.65° = 진폭의 7–8%, 오버슈트 약 0°)에 맞췄다. 처음 기준(Peak > 10°, 지연 > 200 ms)은 일정한 지연만으로 D 0.4에서 멈추게 돼서(D 0.6 예상 Peak ≈ 0.19 s × 62.5 °/s ≈ 11.8° [C]) 2026-11-13에 바꿨다.

### 3.5 표현 모션은 한계 안인가 — **실측 뒤 작성**

- 계산 [C]: 모두 초기 정책 안이다(속도 비 ≤ 0.386, 관절 여유 ≥ 24.4°).
- 그림: 결과 탭 `한계 지도`(`limit_map.png`)에 모션 8개와 R3 단계를 같은 축(요구 Stewart 속도 비 × 최고 관절 가속, [C])에 놓고, 실제 로봇에서 실행한 것과 R3에서 무너진 단계를 표시한다 [M].
  Neutral(linear)은 시작·끝의 속도 계단 때문에 계산 가속이 크게 나온다(200 Hz 표본, 이론상 무한대; 그림 1 아래 칸 설명).

### 3.6 안전 절차 (요약)

- **시작 전**: 이 PC 하나만 로봇을 조작한다(대시보드 앱·다른 PC·CLI 동시 조작 금지). 머리를 받칠 사람과 전원 스위치.
- **연결**: `연결` 버튼이 로봇 상태를 읽고(GET) 연결한다. 토크가 꺼진 로봇이면 지금 자세에서 토크를 켠다(움직이지 않음). 명령 전에 머리가 0.5°보다 많이 움직이면, 토크를 켠 뒤 2°보다 많이 움직이면 멈춘다(`backends/robot_connect.py`).
- **깨우기**: SDK 1.11.0 Wake-up(INIT까지 2 s, roll 20° 갔다 옴).
- **실행 범위**: 사람이 누른 시행 1개만(정책 검사 통과), 로봇에서는 '모두 실행'이 없다. R3는 한 단계씩, D < 0.2 s는 실제 로봇에서 거부.
- **정지**: `■ 정지` = 경로를 따라 0.3 s 감속 뒤 그 자리(S1). 측정이 끊기거나 전송이 늦으면 즉시 정지(S2), daemon 오류면 S3.
- **끝**: 머리를 받치고 `토크 OFF`(상태 메시지를 최대 3개 읽어 disabled 확인) 또는 `연결 끊기`(토크 유지).
- **결과**: 로봇 손상 없음 (실측 뒤 기록)
